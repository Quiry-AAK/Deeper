# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Deeper" — a 2D pixel-art top-down action roguelike (vertical mine descent) built in Unity 6000.0.58f1 (URP 2D Renderer, new Input System). The codebase is in an early state: project scaffolding, full design/engineering documentation, and a first slice of gameplay code — player prefab, a weapon-only run loadout, 8-directional movement with mouse aim, a pose-driven animation rig, the Katana's attack state machine with its Ultimate/Combo/hitstop feel layer, a follow camera and a single test room. That room lives in `Assets/_Main/Scenes/TestScene.unity`, the **development sandbox every system is built and tuned in before it reaches a real game scene** — owner-directed working order for the whole project, documented in `Docs/Engineering/02-TEST_SCENE.md`. A damage pipeline exists as of the training-dummy pass: `Damageable` (health for player and enemies alike), `AttackHitbox` (opens on the Active phase, reports `Landed`/`Missed`), `ContactDamage`, `HitFlash`, and a test-only `TrainingDummy` prefab. Hitstop, camera shake, Ultimate Gauge fill and Combo stacks now all hang off **contact**, not off the swing — a whiff gives nothing. The **Biome 1 basic enemy roster** now exists on placeholder art — Cave Crawler, Rock Slinger, Tunnel Brute and the Elite Deep Warden — each chasing, telegraphing, attacking and dying, with stats driven by `EnemyDefinition` assets in `Data/Enemies/`. The training dummy stays as the thing that never dies. There is still **no player death / run-end** (four enemies can now actually kill her, and `Damageable.Died` still has no subscriber on the player) and **no Dig-Dash**, so `AttackStateMachine.CanCancel` remains exposed and unused. Divergences from locked design are recorded in `Docs/00-DESIGN_CHANGE_BRIEF.md`, including three around the Ultimate: the gauge fills a flat 1% rather than BALANCE §4's per-weapon table, it fills on taking damage at base where that is an upgrade, and — the one that is a live gameplay hole rather than a stale document — the buff Ultimate still **consumes the Combo Counter and discards it**, where CORE_SYSTEMS §4 converts those stacks into bonus damage a buff has none of.

The protagonist is a **single fixed character** — a woman in a short cape and light armour. There is no body/gender selection and no armor system. A narrative layer was added at the owner's direction and lives in `Assets/_Main/Docs/Design/10-NARRATIVE.md`; it is **not locked** and conflicts with the GDD pitch in ways that file lists explicitly.

## Source of truth — read before touching gameplay code or design

- `Assets/_Main/Docs/Design/01-GDD.md` through `09-DESIGN_RULES.md` are the **locked design source of truth** (game overview, core systems, content tables, balance numbers, art budgets, level design, day-by-day plan, MVP scope tiers, and the 14 process rules in `09-DESIGN_RULES.md`). Do not invent mechanics, numbers, or systems that contradict these docs — flag conflicts instead of silently resolving them (Design Rule 9, 11, 12).
- `Assets/_Main/Docs/Engineering/00-IMPLEMENTATION_PLAN.md` is the **engineering checklist**, mirroring the design plan's 7 milestones (M0 scaffolding → M6 Final Boss/Hub) with per-milestone Goal/Systems/Dependencies/Files/Order/Definition-of-Done/Risks. Check it before starting work to see what milestone is current and what's already done; update its checkboxes and notes in the same pass as any implementation change.
- `Assets/_Main/Docs/00-DESIGN_CHANGE_BRIEF.md` is the **single record of everything that now contradicts the locked design docs** — the designer handoff. Every owner-directed divergence, every number engineering had to invent because no doc specifies it, and every conflict *between* locked docs goes here, tagged DECIDED / PROPOSED / CONFLICT, rather than being written into `Design/`. **Add to it in the same pass as any work that diverges** (Design Rules 11/12), and correct it when a recorded item later changes — two of its entries had gone stale by describing behaviour that was subsequently cut or overridden. It feeds a single coordinated Rule 14 reopen, not per-doc edits.
- `Assets/_Main/Docs/Engineering/02-TEST_SCENE.md` describes **`TestScene`, the development sandbox every system is built and tuned in first** — its contents, its cheat keys, the rule that keeps it usable (everything testable lives in a prefab or a component, never authored only in the scene), and why a scene per mechanic was rejected. Read it before adding anything to that scene or to `Scripts/Testing/`.
- `Assets/_Main/Docs/Engineering/01-VERIFICATION.md` records **environment-specific gotchas for verifying work** — the editor freezing the player loop when unfocused, simulated key input never reaching play mode, screenshots being unusable in this window layout, and the `execute_code` constraints. Read it before trying to verify anything in play mode or visually; re-deriving it wastes a lot of calls.
- Keep design and engineering strictly separate: design docs define *what* the game does, engineering docs define *how* it's built. An engineering limitation that seems to require a design change should be raised, not silently implemented as a design change.
- **Milestone order is not binding.** The project owner directs what gets built next, in whatever order they choose; the engineering plan is a running checklist of what exists, not a gate sequence. Mark items resolved as they're completed, and give owner-directed work that falls outside the milestone plan its own tracked section there. Still build one concrete objective at a time rather than speculatively scaffolding ahead.
- **Resolved:** the old equipment/inventory conflict is gone. The inventory system, armor slots and runtime weapon switching were **deleted** at the owner's direction, in favour of the locked design — a run is one weapon chosen in the Hub and locked for the descent. Armor and helmets return post-launch as **cosmetics only** (no stats, no mid-run swapping), which is why the character rig is still layered. See the Run Loadout section of the engineering plan.
- **Open conflict, narrative:** `Design/10-NARRATIVE.md` introduces a named protagonist, a villain (Zyno), a father-as-final-boss and a story that resolves in one run. This contradicts the GDD pitch ("a lone miner"), changes the Final Boss identity from CONTENT_DESIGN's Depth Warden, and adds a dialogue/story system that appears in no design doc and no MVP tier. It is recorded, not locked — a Rule 14 reopen updating GDD, CORE_SYSTEMS, CONTENT_DESIGN, ART_DIRECTION and MVP together is still outstanding.

## Art

**All art work goes through the `deeper-art` skill** (`.claude/skills/deeper-art/`). Invoke it before generating or revising any sprite, character, equipment layer, tileset, icon or UI asset. It carries the locked art style (**Modern pixel art — not 8-bit/retro**), the palette and lighting rules, the sheet/naming contract the animation rig depends on, and the credit-safe generation order. Art generated without it will misalign against the rig rather than error.

## Commands

This is a Unity project, not a CLI-driven build. There is no package.json/Makefile — building, running, and testing all happen through the Unity Editor:

- **Open/run:** Open the project root in Unity Hub with Editor version `6000.0.58f1` (see `ProjectSettings/ProjectVersion.txt`), then Play from the Editor.
- **Build:** Unity Editor → `File > Build Settings` (no CLI build pipeline configured yet).
- **Tests:** `com.unity.test-framework` is installed but no tests exist yet. Once added, run via Unity's Test Runner window (`Window > General > Test Runner`), which supports running a single test by right-click → Run.
- **IDE:** `Deeper.sln` is the generated solution (opened via Rider or Visual Studio, both configured in `Packages/manifest.json` via `com.unity.ide.rider` / `com.unity.ide.visualstudio`). Don't hand-edit `.csproj`/`.sln` files — Unity regenerates them.

## Architecture (as specified by the design docs — not yet implemented)

The intended architecture, per `Docs/Design/02-CORE_SYSTEMS.md`, centers on a small number of generic systems that get reskinned/reused rather than rebuilt per weapon/biome/enemy (Design Rule 2):

- **`IWeapon` interface** — all 3 weapons (Katana, Bow, Greatsword) implement `BasicAttack()`, `HeavyStrike()`, `Ultimate()`, `OnHitLanded(target)`, `GetAttackTiming()`, so the rest of the game (animation, upgrades, HUD, Ultimate Gauge) never branches on which weapon is equipped. Per the engineering plan, Katana is built as a concrete implementation first (Milestone 1) and only generalized into the interface once one weapon proves the shape (Milestone 2) — deliberately not designed for 3 unknowns simultaneously.
- **Attack State Machine** — every weapon action runs `IDLE → WINDUP → ACTIVE → RECOVERY → IDLE`, with a Dash-Attack Cancel that's only legal during Recovery. Per-weapon timing/damage values are data, not hardcoded, so the same state machine drives all 3 weapons.
- **Single damage event pipeline** — `OnDamageDealt(source, target, amount)` is the one event that HUD, Combo Counter, and Ultimate Gauge all subscribe to, avoiding duplicated hit-handling logic.
- **Ultimate Gauge** — resource-gated (not cooldown-gated); fills per `OnHitLanded`, drains fully on use. Alt Ultimates are a swappable strategy on the `IWeapon` instance, not a separate system.
- **`HazardFront`** — one timer-driven system reskinned per biome (rockfall/cracked tiles, rising water/room geometry, lava flow/scorched ground). Build this generic in Milestone 3 (Biome 1) since Milestone 5 (Biomes 2–3) depends on it being a pure reskin, not a rebuild.
- **Room/Wave system** — floors pull 1–3 hand-authored rooms from a per-biome pool via deterministic shuffle (no live procgen, no branching paths). Wave Rooms are a boolean flag on Combat Room prefabs, not a separate room type.
- **Weighted-draw upgrade/curse pools** — shared upgrade pool + weapon-specific sub-pool + a separately-drawn Curse pool, all through one weighted-draw function with per-biome weight tables. Content (upgrades, curses, enemy stats) is intended to be data-driven (e.g., `ScriptableObject` per entry) so BALANCE.md's placeholder numbers can be retuned without code changes.
- **Boss weapon-check mechanics** — not a separate system; existing boss phase/state logic reads the equipped weapon type at phase transitions.

`Scripts/` under `Assets/_Main/` holds only what's been built: `Stats/` (shared `StatType`/`StatModifier`), `Player/` (`PlayerStats`, `PlayerController`, `PlayerAim`), `Character/` (`RunLoadout`, `WeaponDefinition`, `CharacterLayerView`, `CharacterVisuals`, `AuraVisuals`), `Animation/` (`CharacterAnimator`, `CharacterPose`, `SpriteAnimationSet`, `SpriteAnimationView`), `Combat/` (`AttackStateMachine`, `AttackHitbox`, `Damageable`, `ContactDamage`, `HitFlash`, `ComboCounter`, `UltimateGauge`, `UltimateBuff`, `HitStop`, `HitVFX`), `Enemies/` (`EnemyDefinition`, `Enemy`, `EnemyTarget`, `EnemyChase`, `TelegraphedAttack`, `LungeAttack`, `RockThrow`, `ThrownRock`, `OverheadSlam`, `EnemyDeath`, and `TrainingDummy` — test-only), `Camera/` (`CameraRig`), `Core/` (`RigRefs`, `YDepthSort`, `ActorPool`, `PooledActor`), `UI/` (`LegacyUIFont`, `UltimateGaugeHUD`), `Editor/` (`PlaceholderEnemySheets`, `EnemyAnimationSets` — editor-only art tools) and `Testing/` (`TestSpawner`, `TestControls`, `TestOverlay` — test-only, `TestScene` harness). The remaining subfolders (Weapons, Hazards, Rooms, Upgrades, Meta) are created as work actually needs them, not scaffolded upfront.

**Prefab layout: one GameObject per subsystem, never one GameObject carrying every script.** `Player.prefab` is the reference layout every future actor prefab (enemies, bosses, NPCs) should follow:

```
Player            Rigidbody2D, CapsuleCollider2D, Damageable, PlayerStats, RunLoadout, PlayerController
                  SortingGroup, YDepthSort
├── Visual        CharacterAnimator, CharacterVisuals, AuraVisuals, HitFlash
│   └── Body, Legs, Feet, Chest, Head, Weapon   (SpriteRenderers, sorting order 0–5)
├── Combat        AttackStateMachine, AttackHitbox, HitVFX, ComboCounter, UltimateGauge, UltimateBuff, HitStop
└── Aim           PlayerAim
    └── Reticle   (SpriteRenderer)
```

The root carries only what *is* the character physically: the rigidbody, the collider, the health that the collider's hits feed (`Damageable` sits beside the collider so a hitbox can resolve its target with `GetComponentInParent`, the standard Unity shape — on a child group every overlap would need a whole-rig search), the movement controller that `[RequireComponent]`s that rigidbody, and the run's data (`PlayerStats` + `RunLoadout`, which require each other). The whole rig is on the **Player** layer (6); enemies are on **Enemy** (7). Everything else lives in a named group, one group per subsystem, so the Inspector shows six components instead of sixteen and a script is found by opening the group whose name matches it. Add a new script to the group it belongs to; add a new group only when a subsystem genuinely doesn't fit an existing one. **Group objects stay at local (0,0,0)** — `AttackHitbox` and `PlayerAim` measure offsets from their own transform, so moving a group would silently shift the damage volume and the aim origin.

**Depth sorting: every actor needs a `SortingGroup` + `YDepthSort` on its root.** Whoever stands lower on screen draws in front; at the same level the player wins on `YDepthSort.priority` (player 1, enemies 0). The `SortingGroup` is what makes a rig sort as one unit — without it the six body layers (order 0–5) each fight the world independently and her Head beats every enemy. `YDepthSort` then drives the group's order from the **root** position, because a `SortingGroup` otherwise sorts by its renderers' bounds — i.e. the middle of the sprite, not the feet, which misplaces any actor whose art sits at a different height. Three sorting layers, bottom to top: **`Default`** (tilemaps) → **`Actors`** (characters) → **`Overlay`** (hit flashes, aim reticle; the reticle uses `sortAtRoot` to escape the player's group). **Adding a sorting layer means adding it to the Global Light 2D's target list too** — URP applies 2D lights per sorting layer, and anything on an untargeted layer renders as a black silhouette.

**Cross-group references are wired in the Inspector and fall back to `RigRefs.Find` when empty.** A plain `GetComponent` only sees the group it was called from, so anything reaching across groups (the Combat group reading the animator on Visual) resolves through `Core/RigRefs.cs`, which searches the whole rig including inactive objects. The wiring is what actually runs; the fallback exists so a component dropped on the rig by hand still works and so moving a script between groups stays a drag in the Hierarchy rather than a code change. Consequently `[RequireComponent]` is only for genuine same-object dependencies (a controller and its rigidbody) — never as a way to force two subsystems onto one object.

**`RigRefs.Find` is only safe for a field that is always populated on the rig.** It searches from `transform.root`, and anything spawned under a parent — every pooled enemy, since `TestSpawner` and the room spawners parent what they create — has the **spawner** as its root, not itself. An *optional* field left empty therefore resolves against a sibling actor. This is not theoretical: `Enemy`'s optional `ContactDamage` reference, empty by design on three of four enemies, reached across and rewrote the Cave Crawler's damage to whatever spawned next. For anything optional, or anything the prefab layout already pins to a known object (`Damageable` and `ContactDamage` live on the actor root beside the collider), use `GetComponent`/`GetComponentInParent` instead.

**Actors are pooled, not instantiated and destroyed.** `Core/ActorPool.cs` wraps `UnityEngine.Pool.ObjectPool<GameObject>`; **one pool per prefab, owned by whatever spawns it** — there is deliberately no global registry. `Core/PooledActor.cs` lets an instance return itself without knowing its pool, and is attached by the pool at runtime rather than authored on prefabs; anything unpooled falls back to `Destroy`, so pooling can never be forgotten into a leak. **The rule this imposes on every actor component: a recycled instance never runs `Awake` again, so reset your own state in `OnEnable`** — releasing deactivates and getting reactivates, which is exactly what makes `OnEnable` the correct hook. Health refill, attack cooldowns, in-flight animation clips and projectile velocity all reset there. Anything counting live actors must count *active* instances, because pooled ones are deactivated children rather than nulls.

**Moving a component between groups: edit the YAML, don't copy/paste the component.** Unity's copy-component/paste-as-new assigns a **new** fileID, which silently nulls every serialized reference pointing at it. Instead, change that component's `m_GameObject` in `Player.prefab` and move its `- component:` entry between the two objects' `m_Component` lists. The fileID is preserved, so all wiring — including references from other prefabs and scenes — survives untouched. This mirrors the GUID rule for renaming scripts below, and is how the original single-object player was split.

**Character sprite layering.** `CharacterLayerView` is the shared base for anything drawing the layered character; `CharacterVisuals` is the world-rig implementation over `SpriteRenderer`s. Two layers are live — the protagonist's body (fixed art, not a choice) and the run's weapon. The four ex-armor renderers stay wired as `cosmeticRenderers` and are force-disabled on enable, so no stale gear art survives and the post-launch cosmetic pass has somewhere to draw. **Every body-layer sprite shares one 32×48 canvas and pivot** — that, plus a fixed draw order (Body, Legs, Feet, Chest, Head, Weapon = sorting order 0–5), is the only thing aligning the pieces. Real art must preserve both.

**Renaming a script without breaking prefabs.** Unity resolves `m_Script` by the GUID in the `.meta`, so `git mv` **both** the `.cs` and its `.cs.meta` and every prefab/scene reference survives the rename — only serialized *field* names need fixing. This is how the equipment classes were renamed in place without turning `Player.prefab` into missing scripts.

**Animation is pose-driven, not Unity `Animator`-driven.** `CharacterAnimator` owns one (state, facing, frame) pose and raises `PoseChanged`; every layer resolves its sprite from that same pose through the piece's `SpriteAnimationSet`. This is what keeps body and gear frame-locked — a paper-doll rig driven by Unity `Animator`s would need one controller per layer kept in sync. Don't add per-layer animators.

**Facing is 8-way, drawn with 5 authored directions.** `Facing` has all eight compass directions (`CharacterAnimator.FromDirection` snaps a vector by 45° octant). `Facing.ToArt()` collapses those onto five authored rows — Down, Up, Side, DownDiagonal, UpDiagonal — and the three left-hand facings reuse their right-hand art mirrored (`Facing.IsMirrored()` → `flipX` on renderers, negative X scale on UI Images). This is ART_DIRECTION §3's "8-directional, can mirror for 4 base directions": authoring eight separate sets would nearly double the character art budget for no visual gain. Add new directions by extending `FacingArt` and the `Clip` struct together, never by adding art rows alone.

**Sprite sheets — two contracts, one for the player rig and one for enemies.** Sub-sprites are always named `<piece>_<row>_<col>`, row 0 is the top row, cells are 32×48 at 32 PPU with a Center pivot, and everything is referenced by the `SpriteAnimationSet` assets in `Data/Animation/`.

*Player rig:* rows are `Idle Down/Up/Side/DownDiag/UpDiag` then the same five for `Move` (10 rows), **five authored directions**. Current **placeholder** sheets in `Art/Placeholder/Sheets/` are 4 columns; **real art targets 6 columns** — Idle uses columns 0–3, Move uses 0–5 — per the `deeper-art` skill.

*Enemies:* **12 rows × 4 columns (128×576)**, and only **three authored directions** — Down, Up, Side — with each clip's `DownDiagonal`/`UpDiagonal` arrays pointed at the *same sprites* as `Side`, so `Facing.ToArt()` still covers all eight facings with no code change. Rows are Idle/Move (0–2, 4 frames), Telegraph (3–5), Attack (6–8), Death (9–11), the last three clips being 3 frames per `ART_DIRECTION` §4's enemy budget. `Idle` binds one frame and `Move` all four from the same rows, or a standing enemy walks on the spot. Only cells with art are sliced — 39 sub-sprites, not 48. Generated by `Deeper/Generate Placeholder Enemy Sheets` and bound by `Deeper/Bind Enemy Animation Sets`, always in that order. **This enemy contract does not exist in `ART_DIRECTION` §4** — it was invented here and is recorded in the engineering plan pending a Rule 14 pass; 8-directional art is reserved for bosses. Differing clip lengths need no code change, because `SpriteAnimationSet.Resolve` wraps against each clip's own array length. Any reslice regenerates sub-sprites and silently nulls existing references, so **rebind the animation sets after every reimport**.

**`PlayerStats` is the shared stat pipeline.** Anything that changes a player number — the run's weapon now, run upgrades (Milestone 4) and Hub Core Stats (Milestone 6) later — registers a named bundle of `StatModifier`s via `SetSource(key, modifiers)` and removes it by the same key, rather than mutating player numbers directly. Flat modifiers sum into the base value; percent modifiers sum with each other and apply once, matching BALANCE.md's "percentages are additive unless noted". Its `StatType` vocabulary intentionally mirrors the Hub Core Stats table so all three systems speak the same language.

## Code and objects must be easy to understand

**Owner-directed, applies to every pass.** The project owner reads this codebase and inspects these prefabs directly, so legibility outranks cleverness. Concretely:

- **One responsibility per class and per GameObject.** If a class needs "and" to describe it, or a GameObject's Inspector needs scrolling, split it. This is the same rule the prefab layout above enforces.
- **Name things after what they are on screen or in the design docs** — `UltimateGauge`, `ComboCounter`, `HitStop`, `HitVFX`. A reader who knows the game should recognise the class from its name alone, without opening it. Avoid `Manager`, `Helper`, `Handler`, `Utils`.
- **Wire references in the Inspector**, so the connections are visible in the editor instead of discovered at runtime. Runtime searching (`FindFirstObjectByType`, `RigRefs.Find`) is a fallback, not the design.
- **Tunable numbers are serialized fields with a `[Tooltip]`**, never consts or magic numbers in expressions — BALANCE.md's values are placeholders (Design Rule 8) and must be retunable without a recompile.
- **Comments explain *why*, never *what*.** The existing files are the reference standard: they record the alternative that was tried and rejected, the measurement behind a number, or the bug the line prevents. A comment restating the code is noise; a missing "why" costs the next reader an hour.
- **Prefer the obvious Unity shape.** No reflection, no generic indirection layers, no inheritance beyond the one abstraction that earns it (`CharacterLayerView`). If a feature seems to need a framework, that's the signal to raise it, not to build one.
- **Keep files short enough to read in one sitting.** When one grows past ~300 lines, that's the prompt to check whether it is doing two jobs.

## Repo conventions

- All gameplay assets live under `Assets/_Main/` (`Art`, `Audio`, `Data`, `Docs`, `Input`, `Materials`, `Prefabs`, `Scenes`, `Scripts`); `Assets/Settings` holds URP/render-pipeline config generated by Unity's project template and is left alone.
- `Assets/_Main/Data/` holds authored `ScriptableObject` content assets (currently `Data/Weapons/`, `Data/Animation/`, `Data/Enemies/` and `Data/Tiles/`). This is where the data-driven content the design docs describe as *tables* — upgrades, curses, enemy stats, Hub Stat costs — should go, so BALANCE.md's placeholder numbers can be retuned without code changes.
- `Assets/_Main/Art/Placeholder/` is procedurally-generated programmer art (flat colour blocks), not a style reference — it exists only to make layering verifiable before real art lands. Replacing a piece is a sprite swap on the gear asset's `bodyLayer`/`icon` fields; no code changes. Sprites import at 32 PPU, Point filter, uncompressed (ART_DIRECTION §1).
- `.gitattributes` treats Unity YAML assets (`.mat`, `.anim`, `.unity`, `.prefab`, `.asset`, `.meta`, `.controller`) with `unityyamlmerge` and LF line endings — don't hand-normalize these.
